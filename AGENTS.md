# Гайд для агентов

Инструкции для ИИ-агентов, которые пишут и проверяют этот справочник. Люди тоже могут его читать: здесь описано, чего ждать от агента и как ставить ему задачи.

Справочник — это сайт на MkDocs Material и одновременно хранилище Obsidian (папка `docs/`). Язык — русский. Цель — точный справочник по разработке под Sega Genesis / Mega Drive, где каждый факт прослеживается до первоисточника.

Полные правила оформления — в `docs/about/conventions.md`. Прочитай их перед первой правкой. Ниже — главное и порядок работы.

## Главные правила

1. **Никаких фактов из головы.** Каждое утверждение о железе (адреса, биты, лимиты, тайминги, поведение) должно опираться на источник из реестра `docs/sources/index.md`. Если источника нет — найди его и добавь в реестр, или явно пометь утверждение плашкой `> [!todo]` «не проверено».
2. **Не завышай проверку.** Поле `verified` поднимается только после реальной проверки: `sources` — сверено с документами, `emulator` — код собран и запущен в эмуляторе, `hardware` — только если владелец проверил на консоли. Указывай в `sources`, чем проверял.
3. **Расхождения не скрывай.** Если источники противоречат друг другу — опиши оба варианта в плашке `> [!question] Расхождение в источниках` со ссылками на оба.
4. **Авторское право.** Пересказывай своими словами, цитаты — не длиннее одного-двух предложений. Не клади в репозиторий копии документов, если лицензия этого не разрешает (официальные мануалы Sega — никогда).
5. **Держись задачи.** Меняй только страницы, относящиеся к задаче. Нашёл ошибку в другом месте — сообщи о ней или поставь `> [!todo]`, не переписывай молча.
6. **Сборка должна проходить.** Перед завершением: `mkdocs build --strict` без ошибок и предупреждений.

## Структура репозитория

```
docs/                   страницы сайта = хранилище Obsidian
  hardware/             как устроено железо (справочник)
  guides/               пошаговые руководства
  cookbook/             приёмы: задача → решение → код
  tools/                инструменты
  debugging/            эмуляторы и отладка
  interactive/          интерактивные виджеты
  reference/            глоссарий, подводные камни, теги
  sources/index.md      реестр источников (ID в заголовках {#id})
  about/                о проекте и правила
  _templates/           шаблоны страниц (не публикуются)
  assets/               css, js, картинки
examples/               полные примеры кода (собираются отдельно)
sources/                локальные копии документов (только с разрешённой лицензией)
hooks/page_meta.py      плашка статуса и проверка ID источников
mkdocs.yml              настройки сайта и меню (nav)
```

## Типовые задачи

### Заполнить заготовку (`status: stub`)

1. Прочитай план раздела на странице — это минимальный объём.
2. Найди первоисточники. Предпочитай официальную документацию и проверенные описания сообщества (см. реестр).
3. Напиши страницу по шаблону `docs/_templates/page.md`: как устроено → как работать → примеры → подводные камни → см. также.
4. Неочевидные утверждения пометь сносками на источник с указанием раздела.
5. Обнови frontmatter: `status: draft`, `sources: [...]`, `verified` — по факту.
6. Удали чек-лист плана или оставь невыполненные пункты как `> [!todo]`.
7. Добавь новые термины в `docs/reference/glossary.md`, частые ошибки — в `docs/reference/pitfalls.md`.

### Сверить страницу с источниками (`verified: none` → `sources`)

1. Пройди по каждому факту на странице и найди его в источнике.
2. Неверное — исправь. Не найденное ни в одном источнике — пометь `> [!todo]`.
3. Добавь сноски и заполни `sources`.
4. Поставь `verified: sources` только если сверено всё, кроме явно помеченного `todo`.
5. В отчёте перечисли, что исправлено и что осталось непроверенным.

### Добавить источник

1. Найди рабочую ссылку. Если оригинал мёртв — найди копию в Wayback Machine.
2. Добавь запись в `docs/sources/index.md` в нужную группу: заголовок `### Название {#id}` и поля «Что», «Ссылка», «Архив», «Локальная копия», «Статус ссылки» (с датой проверки).
3. Локальную копию клади в `sources/` только если лицензия разрешает. Укажи лицензию в записи.

### Добавить пример кода

1. Пример — отдельная папка `examples/<sgdk|asm>/<NN-название>/` (см. `examples/README.md`).
2. Пример должен собираться. Если собрать нечем — так и напиши в README примера и не ставь `verified: emulator`.
3. Если запускал в эмуляторе — приложи скриншот `screenshot.png` в папку примера.
4. Вставь код в страницу через `--8<-- "examples/..."`, не копируй.

### Добавить интерактивный виджет

1. JS — в `docs/assets/js/`, подключение — в `extra_javascript` в `mkdocs.yml`. Стили — в `docs/assets/css/extra.css`.
2. Виджет ищет свой контейнер по `id` и ничего не делает, если контейнера на странице нет.
3. Без внешних зависимостей и CDN, если без них можно обойтись.
4. Логика виджета должна совпадать с текстом справочника. Ссылайся на страницу, которую виджет иллюстрирует.

## Команды

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
mkdocs serve            # локальный сайт на http://127.0.0.1:8000
mkdocs build --strict   # проверочная сборка (то же делает CI)
```

## Окружение владельца

На машине владельца (по состоянию на 2026-10-28) установлены `blastem` и `m68k-elf-gcc`. Docker и `vasm` не установлены. Это может измениться — проверяй через `which`.

- [ ] Frontmatter заполнен честно (`status`, `verified`, `sources`).
- [ ] Новые источники есть в реестре.
- [ ] Новые термины — в глоссарии.
- [ ] В отчёте: что сделано, что проверено, что осталось `todo`.
