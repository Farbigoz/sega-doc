# Правила оформления

Единые правила для всех, кто пишет справочник: и для людей, и для агентов. Если правило мешает, сначала поменяйте его здесь, а потом пишите по-новому.

## Язык и термины

- Пишем по-русски, просто и конкретно. Объяснение «на пальцах» приветствуется, но без потери точности.
- При первом упоминании термина на странице — английский оригинал в скобках: «таблица имён (nametable)». Дальше — по-русски.
- Термины берём из [глоссария](../reference/glossary.md). Новый термин — сначала добавить в глоссарий.
- Шестнадцатеричные числа: `$C000` в тексте и ассемблере, `0xC000` в коде на C.
- Биты нумеруются с 0 от младшего. «Бит 15» — старший бит слова.
- Размеры данных: **байт** — 8 бит, **слово** — 16 бит, **длинное слово** — 32 бита (как в документации 68000).
- Единицы памяти: байты, КБ, МБ. Размер экрана — в пикселях и клетках (1 клетка = 8×8 пикселей).

## Разделы: что куда писать

| Раздел | Что писать | Чего не писать |
|---|---|---|
| `hardware/` | как устроено железо: форматы, регистры, лимиты, тайминги | пошаговые туториалы |
| `guides/` | пошаговые руководства «от нуля до результата» | полные справочные таблицы (ссылаться на `hardware/`) |
| `cookbook/` | один приём на страницу: задача → решение → код | теорию с нуля (ссылаться на `hardware/`) |
| `tools/` | установка и использование инструментов | — |
| `debugging/` | эмуляторы, отладчики, приёмы поиска ошибок | — |
| `interactive/` | интерактивные виджеты и наглядные модели | — |
| `reference/` | глоссарий, подводные камни, сводные таблицы | — |

Одна тема — одна страница. Не дублируем: если факт уже описан на другой странице, ставим ссылку.

## Файлы и навигация

- Имена файлов и папок — латиница, `kebab-case`: `level-streaming.md`.
- Страница раздела — `index.md` в его папке.
- Каждую новую страницу добавляем в `nav` в `mkdocs.yml`, иначе её не будет в меню сайта.
- Картинки — в `docs/assets/images/<раздел>/`.

## Frontmatter

У каждой страницы-статьи (не у страниц-оглавлений) есть шапка:

```yaml
---
title: Тайлы
tags: [vdp, графика]
status: draft        # stub | draft | review | done
verified: none       # none | sources | emulator | hardware
sources: [plutiedev, macdonald-vdp]
---
```

| Поле | Значения |
|---|---|
| `status` | `stub` — только план; `draft` — текст есть, но не вычитан; `review` — готово к вычитке; `done` — вычитано и проверено |
| `verified` | `none` — не сверено; `sources` — факты сверены с источниками; `emulator` — код проверен в эмуляторе; `hardware` — проверено на консоли |
| `sources` | ID источников из [реестра](../sources/index.md), по которым сверялась страница |
| `tags` | короткие теги в нижнем регистре: `vdp`, `спрайты`, `dma`, `sgdk`… |

Плашку статуса вверху страницы сайт рисует сам по этим полям. Писать её руками не нужно.

Правила:

- `verified` выше `none` ставится **только** если проверка действительно сделана, а в `sources` указано, чем проверяли. Иначе сборка выдаст предупреждение.
- `status: done` требует `verified` не ниже `sources`.

## Структура страницы

Шаблон — `docs/_templates/page.md` (в Obsidian: «Вставить шаблон»). Обычный порядок:

1. Заголовок H1 и 1–3 предложения: что это и зачем.
2. **Как устроено** — форматы, схемы, таблицы.
3. **Как с этим работать** — порядок действий.
4. **Примеры** — код.
5. **Подводные камни**.
6. **См. также** — ссылки на связанные страницы.

На странице ровно один H1, разделы — H2 и H3.

## Ссылки

- Только обычные Markdown-ссылки с относительным путём и расширением `.md`: `[тайлы](../hardware/vdp/tiles.md)`. Так ссылки работают и в Obsidian, и на сайте.
- **Не используем** `[[вики-ссылки]]`: сайт их не понимает. В настройках хранилища они уже выключены.
- Ссылка на раздел страницы: `[DMA](dma.md#ограничение-128-кб)`. Якорь — это текст заголовка в нижнем регистре, пробелы заменены на `-`.

## Плашки (callouts)

Синтаксис Obsidian — его понимают и Obsidian, и сайт:

```markdown
> [!warning] Заголовок
> Текст плашки.
```

| Тип | Когда |
|---|---|
| `note` | дополнительная информация |
| `tip` | практический совет |
| `warning` | частая ошибка, неочевидное поведение |
| `danger` | может повредить данные или железо |
| `example` | пример |
| `todo` | пробел в тексте, который нужно заполнить или проверить |
| `question` | **расхождение в источниках** (см. ниже) |

## Код

- Ассемблер 68000 — блок ` ```m68k ` (синтаксис Motorola). C — ` ```c `. Команды терминала — ` ```bash `.
- Комментарии в коде — по-русски.
- Короткие фрагменты пишем прямо в тексте. Если фрагмент не собирался и не запускался, в плашке `todo` или в тексте должно быть сказано «не проверено».
- Полные рабочие примеры живут в `examples/`, а в текст вставляются, а не копируются:

  ```markdown
  ;--8<-- "examples/sgdk/01-tile-on-plane/src/main.c"
  ```

  (В настоящей вставке точки с запятой в начале нет. Здесь она экранирует вставку, чтобы показать синтаксис.)

  Так у примера один источник, и сборка упадёт, если файл переедет. В Obsidian такая строка видна как есть, это нормально.

- Один пример в двух вариантах — вкладками:

  ```markdown
  === "Ассемблер"
      ```m68k
      ...
      ```
  === "SGDK"
      ```c
      ...
      ```
  ```

## Схемы

- Mermaid (` ```mermaid `) — для процессов и последовательностей. Работает и в Obsidian, и на сайте.
- ASCII-схемы в блоке кода без языка — для раскладки памяти и битовых полей.
- Битовые поля рисуем так (старший бит слева):

  ```
   15 | 14 13 | 12 | 11 | 10 .......... 0
    P |  PAL  | V  | H  |  номер тайла
  ```

## Источники

Каждый факт должен быть прослеживаемым до первоисточника.

1. Все источники перечислены в [реестре](../sources/index.md). У каждого есть ID в заголовке: `### Название {#id}`. ID — латиница, цифры и дефисы.
2. Во frontmatter страницы в `sources` перечисляются ID всех источников, по которым сверялась страница.
3. Конкретные неочевидные утверждения (числа, лимиты, тайминги, особенности ревизий) помечаем сноской с указанием раздела источника:

   ```markdown
   Во время VBlank через DMA успевает пройти около 7 КБ.[^dma-bw]

   [^dma-bw]: [Plutiedev](../../sources/index.md#plutiedev), статья про DMA.
   ```

4. Новый источник — сначала запись в реестре (что это, ссылка, архив, можно ли хранить копию), потом ссылки на него.

### Расхождения в источниках

Если источники говорят разное, не выбираем молча. Описываем оба варианта:

```markdown
> [!question] Расхождение в источниках
> Источник А утверждает X[^a], источник Б — Y[^b].
> Проверено в эмуляторе: … / не проверено.
```

### Авторское право

- Пересказываем своими словами. Цитаты — короткие (одно-два предложения) и в кавычках.
- Технические факты (форматы, номера битов, адреса) можно излагать своими таблицами, не копируя оформление источника.
- Копии документов в `sources/` храним только если лицензия это разрешает или есть разрешение автора. Официальные мануалы Sega не храним: только ссылка и, если есть, ссылка на архив.
